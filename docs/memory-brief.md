# 记忆系统设计简报

`@noa/plugin-memory` 的最终决策记录。方案成形于「手写一个轻量记忆系统，可以调用向量模型」，实施中按用户要求参考了 [Honcho](https://github.com/plastic-labs/honcho) 的向量机制。

## 一句话

策展 markdown（整块注入 system prompt）+ 一个本地 JSON 向量索引（记忆条目 + 历史会话），纯 JS 暴力余弦，向量排名与关键词排名用 RRF 融合。没有服务、没有数据库、没有向量库、没有后台烧 token 的 deriver、没有多租户。

## 为什么不用现成的

**Honcho 太重，不适合这个产品。** 它的向量机制拆开看是好的，但整套是 `api + deriver + Postgres/pgvector + Redis`，还要求一个 LLM provider，可选的 LanceDB 只是存储后端之一。对一个「单操作者、单进程、自用」的常驻 agent 来说，运维一个 Postgres 和三个进程去存几千条记忆，成本远超收益。它自己的文档也承认最麻烦的部分（换 embedding 模型）在它那里是**无法就地完成**的——要新起部署、重灌数据、切流量。

**LanceDB / SQLite / pgvector 都不做。** 几千条 × 1536 维的暴力余弦是几毫秒。为这个数量级引入向量库，换来的是一个要跟着升级、要管文件锁、会写坏的新依赖。

**不做自动固化。** 没有「对话结束就自动总结进记忆」的后台 pass。那是一次额外的模型调用，是一个没有人会察觉它错了的组件。只留显式 `memory` 工具，由模型自己决定什么时候值得记。

## 架构决策

**记忆是插件，不是内核。** 一行 `plugins.entries`，操作者一行就能关掉，配置住在自己的行里，内核完全不认识它。

**策展记忆整块注入，不做每轮检索。** `MEMORY.md`（2000 字符）/ `USER.md`（1200 字符）整块追加到 systemPrompt。每轮按 query 取 top-K 会让缓存前缀每轮失效；上限反过来逼着模型自己精简。

**注入点用 `beforeLlmCall`。** 该 hook 只拿到 `ChatRequest`、没有 session scope——记忆本来就是全局的，内核级闭包状态恰好是对的。否掉「加进 context fragment」的原因很具体：fragment 在会话开启时写死进日志，**恢复会话时会一直带着旧快照**，而 QQ 会话是长期复用的，记忆必须能刷新。哈希 + 文件 stamp 双重守卫，块不变就复用。

**向量客户端由 app 构造并注入。** 插件读不到 core 的 provider 配置（`ChatProvider` 不暴露 apiKey），所以走 `reviewer` 同一条路：`@noa/ai` 的 `createEmbedClient` → `app/src/provider.ts` 的 `createEmbedProvider(config)` → `CreateKernelOptions.embedder` → `runtime-env.ts` 提供成 `embeddingsKey` → 插件 `inject`。凭证不重复配置。

**`ctx.get(embeddingsKey)` 而不是 `must`。** 没有 `embedModel` 时根本没有这个服务，那是受支持的状态（关键词检索），不是「缺了个依赖、这行不该加载」。

## 从 Honcho 借来的两件事

**1. RRF 混合排序。** Honcho 的 `src/utils/search.py` 用倒数排名融合把全文匹配与语义匹配合并（`k=60`）。借它的理由：向量排名与关键词排名**不在一个量纲上**（余弦相似度 vs IDF 加权词频），相加或互相设阈值都没有意义；倒数排名丢掉分数只留名次，两条路都排得高的条目胜出，只被一条路捞到的也还在，而且没有相对权重需要调。它的成本只是对已经算出来的两个列表做算术——BM25 需要把词频统计落盘，那才是不适合文件索引的部分。

**2. 相似度地板（`max_distance` 的对应物）。** Honcho 的查询接口收一个 `max_distance`，超出的结果直接丢弃。这一条是修正一个真实缺陷：原先只挡 `similarity <= 0`，而**真实嵌入模型里不相关的文本对余弦也在 0.1~0.3，几乎不会正好正交**——那个判断实际上什么都没挡，一个记忆里根本没有的话题照样会返回它最不相关的 5 条。现在低于 `minSimilarity`（默认 0.25）的向量命中按「没匹配上」处理。不同模型的相似度分布不同（BGE 这类基线明显偏高），所以它是配置项而非常量。

## 从 Honcho 看到但不做的

- **`max_distance` 作为调用方参数** —— 我们的调用方是模型，它没法有意义地设一个余弦阈值。做成行配置，由操作者按自己用的模型定。
- **超采样后去重**（`top_k = limit * 3`，再按 message id 折叠）—— 他们需要是因为一条消息会切多个 chunk。我们用「单个会话最多占 3 条」的硬配额达到同样目的，一次遍历完成。
- **token 计数 + tiktoken 分批**（`max_tokens_per_request` 等）—— 零依赖优先，按字符切（1500 字符）对任何嵌入模型的上下文都安全。
- **启动时校验向量维度**（解 `atttypmod` 并与配置比对，不匹配就崩）—— 我们是单进程单索引，逐响应校验维度（`parseEmbeddingBody` 拒绝混合维度）已经够，且错误离源头更近。
- **多租户 namespace**（`{prefix}.doc.{hash}` / `{prefix}.msg.{hash}`）—— 单操作者自用，没有多租户。
- **显式归一化** —— 他们不做，因为 pgvector / LanceDB 的余弦自己会归一化。我们是暴力点积，所以写入前统一 L2 归一化。

**有一处我们比 Honcho 严**：他们把「embedding 模型不可变」当作**运维契约**而不是可校验的元数据，文档里明确警告「同维度换模型会静默成功、召回质量下降且没有任何运行时提示」。我们把模型名写进索引，检测到变化就整块重建。

## 六处工程加固（实施前用户点名要求）

1. **`episodes.ts` 游标作废** —— 三重判定：`stat.size < offset`、offset 前一字节不是 `\n`、**文件头部行的 sha1 变了**。第三重是必要的：只比 size 抓不到「同尺寸原地重写」。头部行而不是前 512 字节——绝大多数日志在其生命周期的多数时间里都不到 512 字节，哈希前 512 字节会让每次追加都作废游标，把增量扫描彻底废掉。向量复用靠 `meta.textHash`：重扫时同哈希的条目直接搬旧向量，不重烧额度。
2. **中文分词** —— `Intl.Segmenter('zh-CN', { granularity: 'word' })`，零依赖；QQ 场景九成是中文自然语言，`split(/\s+/)` 会把整句当一个词。ICU 分词是上下文相关的，所以额外补 CJK 字符 bigram。
3. **回声污染与短消息噪音** —— 清洗后短于 12 字符的碎消息、`/` 开头的指令消息不入库；`recall` 拿得到 `ToolExecuteContext.sessionId`，默认**按 sessionId 排除当前会话**（比时间 + 相似度启发式干净得多）；拿不到 sessionId 时退到「2 分钟内且余弦 > 0.96 则丢弃」。单会话最多占 3 条结果。
4. **并发 Lost Update** —— `VectorIndex` 在插件闭包内是唯一内存单例；落盘任务在**执行时**序列化活快照（不在入队时捕获），所以 last-writer-wins 是正确的。
5. **预归一化 + 字节对齐** —— 存盘前统一 L2（防全 0 除零），余弦退化成纯点积；解码走 `buf.buffer.slice(buf.byteOffset, ...)` 再构造 `Float32Array`（`Buffer.from(b64,'base64')` 共享内存池，`byteOffset` 不保证 4 对齐，直接构造会抛 `RangeError`），并校验 `byteLength % 4 === 0` 与维度。
6. **条目换行规整** —— `add` / `patch` 入口把 `content` 规整成**物理单行**（内部换行连两侧空白合并为 `; `，剥离模型多写的 `- ` 前缀，压缩空白）。保证「一条记忆 = 物理一行 `- …`」，否则多行 content 会被 parse 拆成多条残缺记忆，`sha1(text)` 寻址和 `old_text` 匹配也会随之不稳。

## 实施中发现并修掉的两个真实缺陷

**单飞锁的活锁。** 最初用「共享 dirty 标志」实现「调用者必须等到一个在它之后开始的 pass」：调用者 A 在跑 pass 时 B 到达，B 置脏并等待；A 跑完看到脏标志就再跑一轮……**两个互相置脏的调用者会让每一轮结束都再排一轮，永不终止**。测试表现为 30 秒超时（不是断言失败）。改成**按 pass 序号判断**：调用时记下已开始的 pass 数，只有序号更大的 pass 才算覆盖自己。每个调用者因此得到一个确定的答案，等待被调用者数量界定。

**哈希前 512 字节的头部设计。** 见加固点 1。

## 与批准方案的偏离

- **加了混合排序**，方案原文写的是「不做 BM25 混合重排（只在向量不可用时降级为关键词）」。用户随后明确要求参考 Honcho 的向量机制，且 RRF **不是 BM25**——它不引入 BM25 需要落盘的词频统计，只是对已有的两个排名列表做算术。关键词从「降级路径」升格为「另一半信号」。
- **没有实现 `historyRetentionDays`**。方案里提过这个配置键，最终没做：索引增长已经由 `maxEpisodeChunks`（默认 4000，按时间淘汰最旧）单独界定，再加一个按天数的保留期是第二个相互作用的旋钮，没有增加能力。
- **新增 `minSimilarity` 配置键**（方案里没有）——见上面「借来的第二件事」。

## 验证

`pnpm build && pnpm -r typecheck && pnpm test && pnpm lint` 全绿：9 个包类型检查通过，74 个测试文件 / 845 个用例通过（其中 `plugin-memory` 67 个），lint 0 error（40 个 warning 全是既有的）。

加固点各有针对性用例：游标三重作废（含同尺寸重写）、中文分词、当前会话回声排除、并发写不丢更新、全 0 / 未归一化向量、多行 content 规整、低于地板不返回、关键词救回被向量拒绝的条目。
